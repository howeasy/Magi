## Opportunities, ranked by value to Magi

### 1. RPC host tools and host URI schemes: give a headless worker, local or over ssh, Magi's tools and the card's files over the rpc pipe it already has

**What it is.** An `--mode rpc` client can register its own tools (`set_host_tools`) and URL schemes (`set_host_uri_schemes`).
- **Host tools.** When the model calls one, omp writes `{type:"host_tool_call", id, toolCallId, toolName, arguments}` and waits for `{type:"host_tool_result", id, result:{content:[…]}, isError?}`. It also accepts `host_tool_update` partials and sends `host_tool_cancel` when a call is aborted.
- **Host URIs.** A registered scheme sends every `read <scheme>://…` back to the host as `host_uri_request {id, operation, url, content?}`. A `write` to the scheme does the same when the scheme is `writable:true`. The host answers with `host_uri_result {id, content, contentType?, isError?, error?}`.

**Evidence.**
- 18.11.3 source, VERIFIED:
  - Commands: `src/modes/rpc/rpc-types.ts:67-68`.
  - Frame types: `rpc-types.ts:772-857`.
  - `RpcHostToolBridge.requestExecution`: `src/modes/rpc/host-tools.ts:79-150`.
  - `RpcHostUriProtocolHandler`: `src/modes/rpc/host-uris.ts`. A write is offered only when `writable` is set, at tier `"write"`.
  - Docs `rpc.md`, sections "Host Tool Sub-Protocol" and "Host URI Sub-Protocol". New non-hidden host tools "are enabled automatically".
- 18.10.4 binary, VERIFIED:
  - `case "set_host_tools"`: rpc-mode-7cbqkfvr.js+65011, exe@197097220.
  - `case "set_host_uri_schemes"`: exe@197098012.
  - `type: "host_tool_call"`: exe@196996045.
  - `type: "host_uri_request"`: exe@197000803.
- 18.11.3 ELF, VERIFIED: `case "set_host_uri_schemes"` elf@167833309; `type: "host_tool_call"` elf@167726575; `type: "host_uri_request"` elf@167731333.
- **Minimum version.** Present in 18.10.4 (VERIFIED). The 18.5.1 changelog says the published wire schema and generated clients include "host tools, and host URIs" (`CHANGELOG.md:894`). So the feature is at least 18.5.1 old (INFERRED); the exact first release was not checked.

**How Magi could use it.** Magi already holds every headless omp worker on rpc stdin and stdout, both locally and through `ssh <host> … omp --mode rpc` (`src/omp-launch.mjs`, `src/remote-worker.mjs`). Over that same pipe it could add:
- **A read-only `magi://` scheme.** The worker would read a card file as `read magi://card/<id>/files/<name>`, and the bytes would come from the orchestrator's machine inside the rpc stream. Nothing lands on the remote disk first, and Magi need not be installed there. This fits "files sent with card traffic" directly. (INFERRED design; the mechanism is VERIFIED.)
- **Host tools,** for example `ask_orchestrator`, which would open a question card back to the caller, or `report_progress`. Today a headless worker's own MCP servers start, and `magi serve` exits on `PEER_DEPTH=1` (comment in `src/omp-launch.mjs`). Host tools would give the worker exactly the Magi surface the card allows, scoped to one run, with no MCP process on the remote machine. (INFERRED.)

**Not checked; do by hand first.**
- Whether `--tools read,grep,glob,web_search` filters host tools out.
- What approval tier a host tool has on a no-UI rpc host. Any prompt-tier tool there throws "requires approval but no interactive UI available" (`src/extensibility/extensions/wrapper.ts:397-412`, VERIFIED).
- Whether `read` of a host URI needs more than the read tier.

**Suggested change.**
- In `ompRpcSession` (`src/omp-launch.mjs`), send `set_host_uri_schemes` (and later `set_host_tools`) after `set_event_filter`, and answer `host_uri_request` / `host_tool_call` frames.
- Teach `test/helpers/fake-cli.cjs` the same frames.
- Start with a read-only `magi://` scheme for card files.
- Record the real-binary check, with its version, in `docs/transport-recon.md`.

### 2. "Blocked on approval" and the real approval mode for live omp sessions; on 18.11.x a Magi steer denies a pending approval

**What it is.** An extension can subscribe to two events:
- `tool_approval_requested {sessionId, toolCallId, toolName, reason?, approvalMode}`
- `tool_approval_resolved {sessionId, toolCallId, toolName, approved, reason?}`

They are emitted only when a handler is registered for one of them.

**Evidence.**
- 18.11.3: the event types are at `src/extensibility/extensions/types.ts:1243-1259` (VERIFIED). They are emitted in `src/extensibility/extensions/wrapper.ts:369-393`, guarded by `hasHandlers("tool_approval_requested") || hasHandlers("tool_approval_resolved")` (VERIFIED).
- `ApprovalMode` is `"always-ask" | "write" | "yolo"` at `src/tools/approval.ts:18` (task agent).
- 18.10.4: `"tool_approval_requested"` at cli-n7t2g7nn.js+5458, exe@188278846; `"tool_approval_resolved"` at exe@188278900 (VERIFIED).
- 18.11.3 ELF: elf@158710787 (VERIFIED).
- **Minimum version:** 18.10.4 or earlier.

**How Magi could use it.**
- Today the extension cannot see that a session is waiting on a permission prompt. Magi shows Claude as `blocked: permission prompt` but omp only as busy or idle (docs/parity.md, row "Know whether a peer is working, idle or blocked").
- Handling the two events in `omp/magi-omp-extension.js` would give `status:'blocked'` with `waitingFor:<toolName>`.
- The event's `approvalMode` would also replace `approvalModeFromArgv()` and the bridge's cached `omp config get tools.approvalMode` (`src/omp-launch.mjs:16-27`), at least once a session has asked once. (INFERRED design; the event is VERIFIED.)

**The behaviour change behind it (18.11.0).** While a tool approval is pending in the TUI, a user message queued as **steering** denies the pending call and is delivered as the reason.
- Source: `src/modes/controllers/extension-ui-controller.ts:665-705`, "a user message queued as steering while the call waits … denies the call" (VERIFIED).
- Changelog: CHANGELOG.md:181, 18.11.0: "sending a message denies the call and steers the turn with it" (VERIFIED).
- In `AgentSession.#queueUserMessage` (`src/session/agent-session.ts`, VERIFIED), `deliverAs:"steer"` goes to `agent.steer`, the steering queue. `deliverAs:"aside"` goes to `#irc.queueAside`.
- So a Magi **steer** into an omp session that is waiting on approval denies that tool call on 18.11.x. An **aside** should not. (INFERRED from which queue each lands in; not run.)

**Suggested change.**
- **Extension:** on `tool_approval_requested`, call `setStatus('blocked')` with `waitingFor` and `approvalMode`; on `tool_approval_resolved`, return to busy.
- **Engine:** treat omp `blocked` the way it treats Claude's `blocked`, and send an aside rather than a steer to a blocked omp unless the caller asked to interrupt.
- **Docs:** record the 18.11 denial rule in transport-recon.md section 2.

**Corrected 2026-10-16 (fact-check): no idle race.** This section first said, from `agent-session.ts:9160-9167` and `:9194-9222`, that an explicit `deliverAs:"steer"` or `"followUp"` only queues and never starts a turn on an idle session, so a session going idle between the extension's `ctx.isIdle()` check and its send would strand the message. That stopped reading too early. The queue helper then calls `#scheduleIdleQueueDrain()` (18.11.3 `agent-session.ts:8691`, scheduler `:8695-8754`), which runs `agent.continue` (`:4821`). An idle steer therefore starts a turn on its own, and so can a followUp, when its context-tail gate allows. The same chain is in the 18.10.4 binary (exe@192815773-192818616, continue at exe@192750504). `"aside"` on an idle session reaches `prompt` (`:9194-9221`), as said. Aside stays the right choice for a blocked omp, for the 18.11 denial rule above, but not for this race.

### 3. Turn off Magi's own MCP servers in a headless worker per run, with the `--config` overlay Magi already writes

**What it is.**
- Each MCP server is also an extension with id `mcp:<name>` (`toExtensionId: server => \`mcp:${server.name}\``, `src/capability/mcp.ts:114`, VERIFIED).
- The capability loader drops any id listed in the `disabledExtensions` setting (`src/capability/index.ts:150-156`, VERIFIED).
- A `--config` overlay can set any registered setting, and overlays rank above the project and user config (precedence at `src/config/settings.ts:879-890`, task agent).
- An overlay therefore holding `disabledExtensions: ["mcp:magi", "mcp:magi-codex"]` stops those servers starting for that one process.
- 18.10.4 has the same id form: template `mcp:${` at cli-x3y6xvqj.js+177086, exe@183584020 (VERIFIED string). Its use in `disabledExtensions` was not traced in 18.10.4 (INFERRED to hold).
- **Minimum version:** at least 18.10.4 for the string; the behaviour is checked in 18.11.3 source only.

**Why it matters.**
- omp has no `--no-mcp` flag (task agent: none in `src/cli/args.ts` or `flag-tables.ts`; `enableMCP` is an SDK option, forced off only in ACP mode).
- Magi relies on `PEER_DEPTH=1` making `magi serve` exit at once. That still spawns a Node process per server per worker, and omp warns.
- Two related facts about overlays (task agent, `config/settings.ts:3915-3916`): an overlay **cannot** add MCP servers, and an `mcpServers:` key in one is silently ignored.

**Suggested change.**
- Write a `--config` overlay for every headless omp worker, not only advisor runs. Include `disabledExtensions` for Magi's own servers, then the advisor lines when wanted.
- Keep the `PEER_DEPTH` exit as the backstop.
- Check by hand that the warning disappears and no `magi serve` child starts, then record it in transport-recon.md.
- A design note: arrays replace rather than merge in overlays (`#deepMerge`, task agent). An overlay's `disabledExtensions` would therefore replace the user's own list for that run. That is acceptable for a worker, but should be documented.

**Corrected 2026-10-17 (fact-check, omp 18.10.4 source and binary):**
- An overlay's `disabledExtensions` replaces the user's own list (arrays are
  assigned whole, `config/settings.ts:3923-3946`), so write the union.
- An overlay can reach MCP discovery indirectly through `extensions` roots
  (`sdk.ts:2511-2533`), so "cannot add MCP servers" holds only for its
  `mcpServers` key; `--no-extensions` keeps Magi's workers on the narrow
  path.
- The disable is a startup filter before any connection
  (`capability/mcp.ts:108-114`; `mcp/config.ts:150-164`), so no `magi serve`
  child is spawned for a disabled server.

### 4. The advisor: `--config` can set `advisor.reviewMode` and `advisor.syncBacklog` under `--mode rpc`, so notes can land before the final answer

**Corrected 2026-10-17:** `syncBacklog` takes strings,
`"off" | "1" | "3" | "5" | "strict"` (`advisor/settings.ts:25-39`). A bare
`1` is an invalid enum value and reads as the default, `off`
(`config/registry.ts:608-652`). It is a backlog threshold, not a barrier per
review: `"1"` waits at most 30 s, `"3"`/`"5"` let a single review run on,
and `"strict"` still releases on abort or failure
(`session/session-advisors.ts:687-705`, `advisor/runtime.ts:518-559`). The
primary's `message_end` comes before the awaited turn-end, so advice is not
guaranteed before the final answer. And rpc's protocol defaults are soft:
any configured `advisor.enabled` (global, project, overlay, environment)
survives them (`config/settings.ts:1010-1014`), so `--advisor` is not the
only way the advisor turns on.

**What it is.**
- `--mode rpc` pins every advisor setting to its default (advisor off) with `applyProtocolDefaults("rpc", …)` (`src/main.ts:1914-1918`, VERIFIED).
- The pin skips any setting that some layer configures (`pinDefaultValue`: `if (value === undefined || this.isConfigured(setting)) return;`, `src/config/settings.ts:1010-1015`, VERIFIED).
- `advisor.syncBacklog` is declared with `protocolDefault: ["rpc","acp"]` and default `"off"` (`src/advisor/settings.ts:23-30`, VERIFIED).
- `--advisor` is a runtime override of `advisor.enabled=true` (`src/main.ts:1976-1979`, VERIFIED) and is the only advisor flag (`--help` on both versions).
- Docs `advisor-watchdog.md`:
  - `advisor.syncBacklog` "controls how long the primary waits for each scheduled advisor": `off`, `1|3|5`, or `strict`, which waits without a wall-clock cap.
  - `advisor.reviewMode: agent-end` "reviews only final yields".
  - RPC hosts "use protocol defaults for `advisor.*` instead of inheriting local interactive preferences" (VERIFIED doc text).
- 18.10.4: `protocolDefault` at exe@183842380 and `syncBacklog` at exe@184829624 (VERIFIED strings).

**How Magi could use it.**
- Magi's documented gap: "Magi does not wait for the advisor … a review still running then is dropped" (docs/architecture.md, "What it does not do").
- Adding `advisor: { syncBacklog: 1 }` (or `strict`) to the overlay Magi already writes (`magi-advisor-*.yml`, `src/omp-advisor.mjs`) should make the worker wait for the advisor's review at each boundary. A `concern` would then reach the worker, and Magi's `advice`, before the worker's last message. (INFERRED; not run.)
- `reviewMode: agent-end` would instead get one review of the final answer per run.

**Suggested change.**
- Add an operator setting, for example `MAGI_OMP_ADVISOR_SYNC=off|1|strict`, that writes `advisor.syncBacklog` into the overlay.
- Re-run the "The advisor" check in transport-recon.md with it and record the latency cost.
- The prior recon's open item, "whether an `--config` overlay changes them is untested", is now answered from source: it does (VERIFIED code path; the runtime effect is INFERRED).

### 5. Collab discovery registry: a native, same-user, cross-process view of live TUI sessions

**What it is.**
- With `collab.autoStart: view|control` (default `off`), every interactive omp session hosts a collab room and publishes itself to a private local registry:
  - a file `~/.omp/run/collab-hosts/<entry>.json` holding `{version, instanceId, pid, endpoint, createdAt, token}`, mode 0600;
  - an owner-only Unix socket or Windows named pipe that answers newline JSON `{v:1, token, op:"snapshot"}` and `{op:"link", access, generation}`.
- `omp collab list [--json]` and `omp collab link <instanceId|pid> [--view] [--json]` wrap the registry.
- A snapshot carries `instanceId, generation, pid, sessionId, sessionName, cwd, model{provider,id}, startedAt, participants, relayConnected, inputRequired, busy, access`.

**Evidence.**
- `omp --help` on 18.10.4 and 18.11.3 contains `collab  List active local Collab host metadata without URLs; use collab link <instanceId|pid> to retrieve a control link (--view for view-only)` (VERIFIED, line 99 of both help files).
- `omp collab list --json` returned `{"version":1,"hosts":[]}` on Windows and on devbox (VERIFIED; autoStart is off on both).
- 18.10.4 registry chunk cli-ejasyr2r.js, read directly (VERIFIED):
  - `"collab-hosts"` at exe@188287402;
  - the snapshot validator requires an `inputRequired` boolean and allows `busy` to be missing (exe@188289515);
  - `stale_generation` at exe@188291427;
  - the `snapshot` and `link` ops use a timing-safe token check.
- 18.11.3 source: `src/collab/registry.ts:60-97, 162-164, 290-354, 434-468` (task agent).
- `inputRequired` is `this.#pendingUi.size > 0`, documented as "True while a host-side question is retained for (or shown to) a writable guest" (`src/collab/host.ts:301-304`, VERIFIED).
- 18.11.3 ELF: `collab-hosts` elf@95659756, `inputRequired` elf@94561852 (VERIFIED).
- Docs `collab.md` (VERIFIED doc text): "Third-party dashboards and bridges can build on `omp collab list --json` plus `omp collab link` — or speak the newline-delimited JSON endpoint directly".
- **Minimum version:** the registry is present in 18.10.4 (VERIFIED). 18.10.0 moved "Collab discovery" onto the native owner-only IPC transport (CHANGELOG.md:325, VERIFIED).

**Limits.**
- **It needs the relay.** A room publishes to the registry only after its relay connection succeeds (collab.md, VERIFIED doc text; `publishCollabHost` after connect at `host.ts:500`, task agent).
  - The default relay is `wss://my.omp.sh` (VERIFIED): 18.10.4 exe@179192849; ELF elf@98420608; `DEFAULT_RELAY_URL` in pi-wire `src/index.ts:426`, task agent.
  - The production relay is not distributed: "The production relay is not currently distributed for self-hosting" (collab.md, VERIFIED).
- **TUI only.** Hosting exists only in the interactive TUI (`modes/interactive-mode.ts`, task agent). rpc, print, ACP and SDK sessions never appear.
- **`busy` can mislead.** It is `null` from older hosts and false during scheduling pauses (collab.md, VERIFIED doc).
- **`inputRequired` and approvals.** Whether a pending approval counts toward `inputRequired` depends on approvals going through `#raceCollabDialog`. That is INFERRED from `showCollabAwareApproval` (extension-ui-controller.ts:676-705), not run.

**How Magi could use it.** Only as a second source of liveness and state, beside the extension's `agents` row. When a host is listed, `busy` and `inputRequired` are omp's own words for "working" and "waiting on the user". It cannot replace the extension: it is opt-in, TUI-only and needs the relay. (INFERRED.)

**Suggested change.** Optional. `magi doctor` could report `collab.autoStart` and, when hosts are listed, cross-check them against the `agents` rows. Routing should not depend on it.

### 6. A native cross-machine prompt path exists (a collab guest), but it routes through a hosted relay; record it, do not adopt it

**What it is.**
- **The link.** A full-control collab link is `<roomId>.<base64url(32-byte AES-256-GCM key ‖ 16-byte write token)>`, with relay `wss://my.omp.sh` by default.
- **What a guest can do.** From anywhere, a guest holding it can:
  - send `prompt {text, images?}` and `abort`;
  - send `agent-cmd` with `chat`, `kill` or `revive`;
  - answer host `ui-request`s.
- **How a prompt lands.** The host turns a prompt into `promptCustomMessage({customType:"collab-prompt", attribution:"user", details:{from}}, {streamingBehavior:"steer"})`: a steer while busy, a new turn when idle.

**Evidence.**
- `#handlePrompt`: `src/collab/host.ts:978-1010` (read directly, VERIFIED).
- Write-token check, `host.ts:745-756`, and frame dispatch, `host.ts:702-740` (task agent).
- Envelope `[4-byte peerId][IV | AES-GCM(JSON)]`: `src/collab/protocol.ts:152-173` and `src/collab/crypto.ts:1-58`. `COLLAB_PROTO = 3` (task agent).
- Docs `collab.md`, sections "Guest permission model" and "Architecture notes" (VERIFIED doc text).
- `omp join` refuses to run without a TTY (`commands/join.ts:31`, task agent).
- `omp join` and `omp share` exist in both versions (VERIFIED help).

**Assessment.** This is the only built-in way for one process to put a user message into another running omp without an extension, and it works across machines. Five things count against using it:
- Every payload transits a third-party relay. It is encrypted, but the relay sees room ids, frame sizes and routing prefixes.
- The host must be a TUI session with collab on.
- A guest must implement the AES-GCM protocol and the snapshot stream.
- The prompt lands as a `collab-prompt` **custom message**, not a `type:"message"` user record. Magi's `confirmOmp` receipt scan would not see it.
- Steer is the only delivery; there is no aside.

Magi's own relay over the operator's ssh, plus the extension, stays the better route (INFERRED). docs/parity.md names collab and these limits; its same-harness Magi route remains a proposed `omp_peer` served `--as omp` with a same-session self-call refusal (see the same-harness notes).

### 7. `omp session pack`, `unpack` and `moved`: move a worker's session between machines natively

**What it is.**
- `omp session pack <session.jsonl|id> <archive>` packs a session together with its artifacts and image blobs.
- `omp session unpack <archive> --cwd <dir>` restores it and prints the new session file path.
- `omp session moved <file> --to <name>` marks the local copy as moved, so resuming it later forks instead of continuing.

**Evidence.**
- `omp session --help` is identical on 18.10.4 and 18.11.3 (VERIFIED).
- 18.10.4: the string `session pack` at session-5jrmhwcp.js+2550, exe@194405348 (VERIFIED).
- CHANGELOG.md:319, in 18.10.0 (VERIFIED). **Minimum version: 18.10.0.**

**How Magi could use it.** Today `--resume <id>` works only where the session file is, so a headless omp card cannot be continued on a different `host` than the one that ran it. This would let it (INFERRED):
1. pack on the old host;
2. stream the archive over ssh;
3. unpack on the new host;
4. resume with the printed path;
5. run `moved --to <host>` on the old host.

The same route could hand a finished remote worker's session back for `peers` and history.

**Suggested change.** Only if cross-host continuation is wanted. Otherwise, refuse a continuation whose host differs and name this as the fix.

### 9. `omp auth-gateway`: one set of credentials for workers on other machines

**What it is.**
- **`serve`** is an HTTP forward proxy over the configured auth broker:
  - it needs a broker and binds `127.0.0.1:4000` by default;
  - it authenticates with a bearer token;
  - `--clients=<file>` (new in 18.11.2) adds scoped tokens limited to listed models and broker accounts.
- **`stdio`** serves the same routes as JSON lines with the caller's own sign-ins.
  - Input `{"id","path":"/v1/chat/completions","body"}` gets output `{"id","status","body"}`.
  - The request's `model` takes any `--model` selector.

**Evidence.**
- `omp auth-gateway --help` on both versions (VERIFIED). CHANGELOG.md:998 (18.4.12, `stdio`) and :49 (18.11.2, `--clients`) (VERIFIED).
- Endpoints and the clients schema: pi-ai `src/auth-gateway/server.ts` and `clients.ts` (task agent).

**How Magi could use it.** Not for messaging. It helps only when a remote worker lacks provider credentials (INFERRED). An operator could run `serve --clients=…` behind an ssh `-L` tunnel and point a remote omp's provider at it (`transport: "pi-native"`, task agent). This is out of Magi's scope; mention it as an operator option in docs/security.md.

### 10. `--mode rpc-ui` versus plain `rpc`: keep plain `rpc`

`rpc-ui` speaks the same protocol, but sends tool UI to the host as `extension_ui_request`: `ask`, and approvals as a `select` of `["Approve", …, "Deny"]`.
- Plain `rpc` has no UI. A prompt-tier tool there throws "requires approval but no interactive UI available" (`src/main.ts:2254`, task agent; `wrapper.ts:397-412`, VERIFIED directly).
- Since 18.4.5, `--no-ui` works with both modes (CHANGELOG.md:1157, VERIFIED).

Magi's headless limits (docs/security.md) depend on that throw, so keep `--mode rpc` (INFERRED). A later "worker asks the card for approval" feature could use `rpc-ui` and answer `extension_ui_response` from a question card.

### 11. Smaller items

- **`ssh://host/path` in read, write and grep (security note).**
  - These URLs resolve against configured hosts **or "any destination OpenSSH can resolve itself (e.g. a `~/.ssh/config` alias)"** (`src/internal-urls/ssh-protocol.ts:1-12`, VERIFIED).
  - The scheme is advertised only when `ssh` is on PATH (`:253-256`).
  - Reads and writes are at tier **`exec`** (`readTier: "exec"`, write tier `"exec"`, `:245-251`, VERIFIED).
  - ssh runs with `BatchMode=yes`, `StrictHostKeyChecking=accept-new` and `ControlPersist=3600` (`src/ssh/connection-manager.ts:187-195`, task agent; 18.10.4 `ControlPersist=3600` at exe@164342243, VERIFIED).
  - Consequence: a Magi worker with `allowCommands` (`--approval-mode yolo`) can read and write files on **any host the operator's ssh keys reach**. A review or `write` worker on a no-UI rpc host should fail closed, because exec tier needs approval and the call throws (INFERRED; not run).
  - Add this to docs/security.md, "What a headless peer may do". 18.10.4 has the `ssh://` handler (exe@164353273, VERIFIED string); its tier there was not checked.
- **`omp ssh add|remove|list`** manages `<agentDir>/ssh.json` and `<cwd>/.omp/ssh.json` (task agent: `pi-utils/src/dirs.ts:1167-1172`). It never launches omp remotely or forwards a session (task agent). `omp ssh list --json` returns `{"project":{},"user":{}}` on both machines (VERIFIED). Keep Magi's `remotes.json`.
- **MCP precedence (the observation, explained).**
  - The native provider (priority 100) reads, in this order: `<cwd>/.omp/mcp.json`, `<cwd>/.omp/.mcp.json`, `<agentDir>/mcp.json`, `<agentDir>/.mcp.json` (`src/discovery/builtin.ts:237-241`, VERIFIED).
  - The root-file provider `mcp-json` (priority 5) reads `<cwd>/mcp.json` and `<cwd>/.mcp.json` (task agent: `discovery/mcp-json.ts:170-190`).
  - The first definition wins across providers (`capability/index.ts:231`, task agent; mcp-config.md "Discovery and precedence", VERIFIED doc text).
  - So `~/.omp/agent/mcp.json` beats a project-root `.mcp.json` on a name clash, which is the observation. A project **`.omp/mcp.json`** beats the user file.
  - `disabledServers` in the user file is the top-precedence denylist (`src/mcp/config.ts:128`, VERIFIED).
  - Timeouts: `OMP_MCP_TIMEOUT_MS` overrides every per-server `timeout` for the process; `0` disables it; the default is 30 s (`mcp/timeout.ts:3`, task agent; mcp-config.md, VERIFIED doc).
  - Foreign user configs (`~/.claude*`, `~/.codex`) load only when `enabledProviders` lists them (task agent).
- **`omp acp`** runs omp as an Agent Client Protocol server over stdio (VERIFIED help); MCP is forced off in that mode (task agent: `main.ts:578`). It is a harness-neutral route, but Magi's rpc channel is richer. No change.
- **`omp stream`** broadcasts screens and chat to `https://live.omp.sh`; viewer chat never reaches the agent (task agent: `stream/protocol.ts:40-44`). It is not a channel.
- **`seance`** is a task agent that consults a saved session read-only. Its tools are only read, grep and glob; MCP, extensions, IRC and LSP are off (docs `session-operations-export-share-fork-resume.md`, "Seance", VERIFIED doc; CHANGELOG.md:16, 18.11.3). A possible local primitive for "ask about a past session"; not a cross-machine one.
- **Workflows** are not a first-class feature. Only the magic keyword `workflowz` exists (task agent: `modes/magic-keywords.ts:59-90`). The task tool runs subagents **in-process**, can optionally isolate them in a worktree, and has no host or harness field (task agent: `task/executor.ts`, `task/types.ts:48-99`). Cross-machine fan-out stays in Magi.

## Same-harness notes: omp asking omp on another machine

**What omp itself offers.**
- **In process only:**
  - **IRC** between the main agent and its subagents. Sending is `write agent://<id>` and receiving is the `wait` tool. Delivery is a steer from a parent, an aside from others, or a wake when idle (`src/session/irc-bridge.ts:181-245`, task agent; `src/irc/bus.ts:2`, VERIFIED).
  - **Agent Hub** (docs `agent-hub.md`: "the current session's agent registry").
- **Across machines, natively:** only **collab** (Opportunities 5 and 6). It needs a TUI host with `/collab` or `collab.autoStart: control`, a relay both ends reach (`wss://my.omp.sh`, or a self-run relay, which is only available as a dev stand-in), and the control link.
  - A remote omp can join with `omp join <link>`, but only with a TTY (task agent).
  - Joining shows the host's session in the guest's TUI; it is not a peer call with a reply.
  - Extension-originated turns (`pi.sendUserMessage`, `pi.sendMessage` with `triggerTurn`) are **refused as host-only while joined** (CHANGELOG.md:1009, 18.4.12, VERIFIED). So a Magi extension inside a guest cannot use the guest to prompt the host.
- **Moving work, not talking:** `omp session pack/unpack/moved` (Opportunity 7), and `seance` to consult a saved session read-only.

**What a Magi omp-to-omp route needs** (INFERRED design, built from the verified pieces):
1. **Caller side.** omp A already reaches Magi through its MCP entry (`magi`, `serve claude --as omp`, `timeout: 0`; docs/mcp-config.md). It needs an `omp_peer` tool served `--as omp` to omp. Today an omp session is served `claude_peer` and `codex_peer` only (docs/mcp-config.md: `serve claude --as omp`, `serve codex --as omp`). Serving `omp_peer` to an omp caller means letting the omp adapter accept an omp origin, and a role check that forbids same-session self-calls.
2. **Headless target on machine B:** this works today in shape. `ssh B … omp --mode rpc …` is the route Magi uses for Claude and Codex orchestrators (docs/architecture.md, "A live session on another machine"). Opportunity 1 (a `magi://` scheme and host tools) is what lets worker B read A's card files and ask A questions over that same pipe.
3. **Live target on machine B:** use Magi's relay (`src/relay.mjs`) to B's Magi, then B's extension inbox, as for any live session. Two things change with this research:
   - prefer `aside` over `steer` when B is blocked on an approval (Opportunity 2);
   - read omp's own `blocked` state through `tool_approval_requested`.
4. **Reply path.** B's omp answers with its bridge tool pointing back at the orchestrator. Today that is `claude_peer` or `codex_peer` (docs/architecture.md); an omp orchestrator needs B's omp to hold an `omp_peer` that routes by `originOf` to A. The ledger already routes by recorded origin, so this is the same `--as omp` serving change as step 1.
5. **Collab as a fallback.** It is not worth it: third-party relay, TUI-only, a custom-message receipt Magi cannot confirm (`collab-prompt`), and steer only.
