## Opportunities (ranked by value to Magi)

### 1. Reach a remote machine's Codex the way the desktop does: `ssh host codex app-server proxy`

**What it is.** Since 0.160.1 a machine runs one shared app-server daemon on a
control socket, `~/.codex/app-server-control/app-server-control.sock`.
`codex app-server proxy [--sock PATH]` pipes stdio to that socket. The socket
speaks the app-server JSON-RPC **over WebSocket** at `ws://localhost/rpc`. The
Codex desktop 26.1013 already uses exactly this for its own SSH remote hosts
("ssh_websocket_v0").

**Evidence.**

- VERIFIED: `codex app-server --help` lists `proxy` ("Proxy stdio bytes to the
  running app-server control socket", `--sock <SOCKET_PATH>`) and `daemon`
  (`bootstrap` "Install durable local app-server management for SSH-driven
  use", `start`, `restart`, `stop`, `version`, `enable-remote-control`). The
  help is identical on 0.160.1 and on 0.163.0 (Mac).
- VERIFIED strings:
  - `app-server-control.sock` at 0.160.1 0xf383cb8 and 0.163.0 0xb5f65fa.
  - `ws://localhost/rpc` at 0.160.1 0xf0bb56a and 0.163.0 0xb4c6635.
  - `Install durable local app-server management for SSH-driven use` at
    0.160.1 0xf1d8786 and 0.163.0 0xb4e739f.
- VERIFIED (asar 0x5d5eba): the desktop's local transport opens
  `new Jo({websocketUrl:"ws://localhost/rpc", createConnection:()=>net.createConnection(<codexHome>/app-server-control/app-server-control.sock)})`,
  and probes the daemon with `[app-server, daemon, version]`. Locally that
  path is taken only when not on win32 and `CODEX_APP_SERVER_USE_LOCAL_DAEMON=1`.
  Otherwise the desktop spawns its own stdio app-server.
- VERIFIED (asar 0xa85e66, 0xa8414e, 0xa82fe3): for an SSH host the desktop
  - probes `command -v codex` in a login shell;
  - bootstraps `nohup codex -c features.code_mode_host=true app-server --listen unix:// …&`
    (skipped when `CODEX_SSH_SKIP_APP_SERVER_BOOT=true`);
  - connects a WebSocket client (`perMessageDeflate:false`) whose connection is
    `ssh -T <host> '<PATH setup> && exec codex app-server proxy'`.
  The log events are `ssh_websocket_v0.ensure_remote_app_server`,
  `…proxy_command_starting`, `…remote_app_server_bootstrap_failed` and others
  (21 distinct).
- VERIFIED: the asar's thread catalog keys hosts as `hostKind` `local|ssh`
  (0x7d76d3). Its host configs are `ssh`, `wsl` and `remote-control`
  (`hostConfig.kind===\`remote-control\`` at 0xc8f7a1, `kind:\`ssh\`` at
  0xa94769).
- VERIFIED: the TUI uses the shared daemon by default. The strings
  `Running without the shared background server: … requires embedded mode`
  (0.163.0 0xb38e083, also in 0.160.1) are followed by the reasons
  embedded mode is forced: `-c/--enable/--disable/--search`,
  `--dangerously-bypass-hook-trust`, `--strict-config`,
  `executor selection (CODEX_EXEC_SERVER_URL)`, `--profile`, `--oss` and
  `--no-daemon` (0.163.0 0xb8ca231). Help for `--no-daemon`: "Run without the
  shared background server, even if it is already running".
  **Corrected:** those strings name possible reasons,
  not the rules. `tui/src/daemon_startup.rs:25-103` (rust-v0.160.1) allows
  audited overrides (`--enable worktrees`, `-c tui.fullscreen_transcript=true`
  keep the daemon), and adds exclusions (workload identity, custom config
  loaders) plus other selection paths (`startup_orchestration.rs:494-555`).
  Turning off `daemon_auto_start` is not `--no-daemon`: an eligible launch
  can still attach to a daemon already running. Which server owns a thread
  is read from the connected server, never inferred from flags.
- VERIFIED (0.163.0 symbols): `codex_app_server_daemon::thread_recovery::discard_pending`,
  and a `loaded-threads.json` string beside `app-server-daemon`. INFERRED from
  those: the daemon restores loaded threads after a restart.
- VERIFIED negative: the Mac had no daemon running at 21:07.
  `daemon version` printed `failed to connect to /Users/<user>/.codex/app-server-control/app-server-control.sock … os error 2`.
  The local Windows socket file exists but refused (10061).

**Minimum version:** 0.160.1 (CLI side); desktop 26.1013 as the user of the route.

**How Magi could use it.** This is the strongest single change for the fleet.
For a Codex peer on another machine, the relay (or the near end directly)
holds `ssh <host> codex app-server proxy` and speaks app-server JSON-RPC to
the daemon that owns that machine's TUI threads. That gives:

- Live `thread/list` with real `status` (`active` + `activeFlags`; see 2),
  not the all-`notLoaded` view a second app-server gets (transport-recon.md,
  "Discovery").
- `turn/steer` with `expectedTurnId` into a running turn. That is a remote
  steer with no desktop pipe.
- `thread/queue/add` with Magi's own `clientUserMessageId`.
- Notifications on the same connection: `turn/started`, `turn/completed`,
  `item/completed` with `userMessage.clientId`, `thread/status/changed`,
  `thread/queue/changed`. Receipts arrive pushed, instead of the relay
  polling `thread_history_1.sqlite` there.

What it needs:

1. A WebSocket client over a stream. Node's global `WebSocket` cannot take a
   custom stream, so either:
   - write a ~150-line RFC 6455 client over the ssh stdio (no dependency), or
   - forward the socket, `ssh -N -L 127.0.0.1:<port>:/home/u/.codex/app-server-control/app-server-control.sock`,
     and use the built-in `WebSocket('ws://127.0.0.1:<port>/rpc')`.
   INFERRED: both are untested.
2. A daemon running on the remote. The options are
   `codex app-server daemon start`, `bootstrap`, or the desktop's own
   one-liner. Each is an operator-approved change on that machine.
   **Corrected:** `bootstrap` is not a launchd or
   systemd unit. It is a managed package with saved settings and a
   pidfile-backed detached process (`app-server-daemon/README.md:93-102`,
   `bootstrap_locked` returns `BackendKind::Pid`), and it does not survive a
   reboot (README:130-144).

Limits:

- Threads in a remote desktop's private stdio app-server are not on the
  daemon.
- **Corrected 2026-10-16 (fact-check):** `daemon`
  lifecycle is **Unix and Windows**, not Unix-only. This first read the
  desktop's `process.platform!=="win32"` gate, which picks the desktop's own
  transport, as the CLI's platform limit. The CLI's gate is
  `#[cfg(any(unix, windows))] fn ensure_supported_platform()`
  (`app-server-daemon/src/lib.rs`, rust-v0.160.1, read by me too); on
  Windows, `start`, `restart` and `bootstrap` refuse an elevated launch
  (`backend::windows::ensure_not_elevated`). A Windows remote is in reach;
  not yet run there.

### 2. A blocked session is visible: `ThreadStatus.activeFlags` and `thread/status/changed`

**What it is.** `ThreadStatus` is `notLoaded | idle | systemError | active{activeFlags}`,
and `ThreadActiveFlag` is `waitingOnApproval | waitingOnUserInput`. It is
pushed as `thread/status/changed {threadId, status}`.

**Evidence.**

- VERIFIED: the 0.160.1 and 0.163.0-alpha schemas (`ThreadStatus`,
  `ThreadActiveFlag`, `ThreadStatusChangedNotification`).
- VERIFIED strings: `waitingOnApproval` / `waitingOnUserInput` at 0.160.1
  0xf125990 / 0xf1259a1 and 0.163.0 0xb4f8bba / 0xb4f8bcb.

**Min:** 0.160.1.

**Use.** A remote-peer field test on 2026-10-16 found a session that "sat 11
minutes at its own bash approval prompt and nothing here could see it". For Codex
peers reached through 1, Magi can show `blocked: approval` / `blocked: input`
in `kind:"peers"` and on the deck. It can also hold notes instead of steering
into a blocked turn.

Only the owning app-server knows these flags. For desktop-owned threads use 4
(`wait_threads` "needs attention") or 3 (hooks).

### 3. Codex hooks can call Magi's MCP tool directly (`mcpTool` handler), for any Codex session

**What it is.** Hook events:

- `preToolUse`, `permissionRequest`, `postToolUse`
- `preCompact`, `postCompact`
- `sessionStart`, `sessionEnd`, `userPromptSubmit`
- `subagentStart`, `subagentStop`
- `stop`, `interrupt`

Handler types are `command | mcpTool | prompt | agent`. An `mcpTool` handler
names `{server, tool, input}`, so Codex itself calls a configured MCP server's
tool when the event fires. Hooks carry a trust state
(`managed | untrusted | trusted | modified`, with
`--dangerously-bypass-hook-trust` as the override). App-server clients see
them as `hook/started` and `hook/completed`, and can list them with
`hooks/list`.

**Evidence.**

- VERIFIED: the schemas list `HookEventName`, `HookHandlerType`,
  `ConfiguredHookHandler` (`McpToolConfiguredHookHandler`: `server`, `tool`,
  `input`, `timeoutSec`), `HookMetadata.trustStatus` and `HookSource`
  (`user`, `project`, `plugin`, …).
- VERIFIED: 0.160.1 has the same `HookHandlerType` enum. The user's
  `~/.codex/hooks.json` already uses `SessionStart`, `UserPromptSubmit` and
  `Stop` command hooks.

**Min:** 0.160.1.

**Use.** Install, with consent, a `PermissionRequest` hook and a `Stop` hook
whose handler is `{type:"mcp_tool", server:"magi", tool:"<a status tool>"}`.
Every Codex session then tells Magi when it blocks on approval and when it
finishes a turn: desktop-owned, TUI, exec, local or on a remote. Magi would
stop inferring busy or idle from `thread_turns` plus a 15-minute window
there.

INFERRED:

- the hook payload's fields (session or thread id, turn id), which were not
  inspected;
- that an `mcp_tool` hook can reach the bridge server registered in the same
  config;
- that trust prompts on first use.

Check all three against a live hook before relying on it.

### 4. The desktop's `codex_app` pipe has more than `send_message_to_thread`: `wait_threads`, `read_thread`, `list_threads`, `create_thread`, `handoff_thread`

**What it is.** Desktop 26.1013 defines the tools `list_projects`,
`create_project`, `list_threads`, `list_archived_threads`, `read_thread`,
`create_thread`, `send_message_to_thread`, `wait_threads`, `fork_thread`,
`handoff_thread`, `move_thread_to_project`, `set_thread_pinned`,
`set_thread_archived`, `set_thread_title` and `set_thread_read_state`.

`wait_threads` takes `{targets:[{threadId, hostId?, afterCursor?}] (1..8), timeoutMs (0..120000)}`.
Per its own guidance it "wakes on the first target that completes or needs
attention".

Targets carry a `hostId`: the desktop routes `send_message_to_thread` to
threads on its other hosts (SSH, remote-control). The desktop's own
coordinator prompt tells worker threads to "send a short message back to this
coordinator thread using send_message_to_thread".

**Evidence.**

- VERIFIED tool names: asar 0x40bfed4.
- VERIFIED `wait_threads` schema: asar 0x7ac8f3 and 0x40bfed4.
- VERIFIED guidance text: asar 0xca4b22 and 0x36fd706.
- VERIFIED host routing: in the `Xeu` function, `send_message_to_thread`
  resolves `hostId` before sending (asar 0x40cac63).
- VERIFIED: the plugin `.mcp.json` sets `approval_mode:"prompt"` on
  `create_thread`, `send_message_to_thread`, `fork_thread`, `handoff_thread`,
  `move_thread_to_project` and `automation_update`, and lists
  `omit_tools_from:["deferred"]`.

**Min:** desktop 26.1013 as seen. Not checked on 26.915.

**Use.** Magi already finds this pipe and speaks MCP through the plugin's
`server.mjs`.

- `wait_threads` (with `timeoutMs:0` for a snapshot) would give a desktop
  thread's completion and needs-attention state. That could replace the
  `magi-delivery:` marker scan through `thread_history_1.sqlite` for steer
  receipts and busy state.
- `list_threads` / `read_thread` with `hostId` would expose the desktop's own
  remote SSH hosts to Magi's peers list.

INFERRED:

- that all of these appear in the pipe's `tools/list` (`deferred` tools may be
  withheld unless `CODEX_APP_TOOLS_DEFERRED=1`, asar 0x78ff00);
- the exact result shapes.

Probe `tools/list` with the desktop running.

### 5. Structured context, a structured answer and native tools for headless workers: `additionalContext`, `outputSchema`, `dynamicTools`

**What it is.**

- `TurnStartParams` and `TurnSteerParams` carry
  `additionalContext: {<sourceId>: {kind: "untrusted"|"application", value}}`.
- `TurnStartParams.outputSchema` takes a JSON Schema that constrains the
  final assistant message.
- `ThreadStartParams.dynamicTools` is `[DynamicToolSpec]`, function or
  namespace. Calls to these arrive at the client as the server request
  `item/tool/call`, with items of type `dynamicToolCall`.
- `responsesapiClientMetadata` carries turn metadata.

**Evidence.** VERIFIED: the 0.160.1 schema (`AdditionalContextEntry`,
`AdditionalContextKind`, `DynamicToolSpec`, `ServerRequest`
`item/tool/call`), unchanged in 0.163.0-alpha.

**Min:** 0.160.1.

**Use** (headless worker, `src/codex-launch.mjs`):

- Send the `PEER REQUEST magi/1` header as `additionalContext` with
  `kind:"application"`, keyed `magi`, and keep the user text clean. Mark
  quoted peer replies as `kind:"untrusted"`, so the "recipient knows it is
  not the human" row in parity.md gets a structural answer.
- Use `outputSchema` for REVIEW/VERIFY verdicts that Magi parses.
- Give the worker a native `magi_note` or `magi_clarify` dynamic tool,
  answered over the same stdio channel. Clarify questions then need no MCP
  bridge server inside the worker.

INFERRED: how the model weighs `untrusted` context.

### 6. Put text into a thread's context without starting a turn: `thread/inject_items`

**What it is.** `thread/inject_items {threadId, items:[raw Responses API items]}`
appends to the thread's model-visible history. The response is empty.

**Evidence.** VERIFIED: the 0.160.1 schema (`ThreadInjectItemsParams`:
"Raw Responses API items to append to the thread's model-visible history").
The string `thread/inject_items` is in 0.160.1 (0xf0d9401), 0.163.0
(0xb52554b) and the asar (0xb7ad95, 13 hits), so the desktop uses it.

**Min:** 0.160.1.

**Use.** FYI deliveries that should not wake an idle peer: a late reply to a
thread that moved on, or a file manifest. Only through the owning app-server
(1, or Magi's own headless workers).

INFERRED: whether it is accepted on an active turn, and whether it writes
history items Magi's receipt readers would see.

### 7. A durable card link inside Codex's store: `thread/attachment/*` and `thread/attachmentOwner/list`

**What it is.** These are per-thread attachments:
`{attachmentType, identityKey, payload: any}`, with outcome
`created | existing`, a `thread/attachment/updated` notification and the
`state_5.sqlite` table `thread_attachments`. 0.162 added a reverse lookup,
`thread/attachmentOwner/list {attachmentType, identityKey}`.

**Evidence.**

- VERIFIED: the schemas.
- VERIFIED: the local `thread_attachments` table holds `pull_request` (1) and
  `worktree` (2) rows, which the desktop writes (`thread/attachment/add` at
  asar 0x9ba937).
- VERIFIED: `thread/attachmentOwner/list` is absent from the 0.160.1 schema
  and present in 0.162 and 0.163-alpha.

**Min:** 0.160.1 (add/list/remove); 0.162 (owner lookup).

**Use.** Attach `{attachmentType:"magi.card", identityKey:<taskId>, payload:{round, host}}`
to the peer thread. "Which thread owns card X" then has an answer in Codex's
own store that survives a lost Magi state.

INFERRED: whether the desktop UI renders an unknown attachment type.

### 8. Push instead of poll, and the queue API

`thread/queue/changed {threadId}` and `thread/queue/list|update|delete|reorder|start`
exist, and `QueuedSubmission` carries Magi's `clientUserMessageId`. VERIFIED
in the 0.160.1 schema.

Magi already calls `thread/queue/add` with its own id
(`src/transport.mjs:776`). Through 1 it could subscribe to `queue/changed`
and `item/completed`, and stop reading `queue_1.sqlite` and the history for
receipts on that route.

`codex queue --remote ws://host:port --remote-auth-token-env VAR` also exists
(VERIFIED in the help on 0.160.1 and 0.163.0). It is a native one-shot remote
queue, but only against an app-server listening on `ws://IP:PORT` with
`--ws-auth capability-token|signed-bearer-token`. That is a LAN listener, a
bigger exposure than ssh.

### 9. Ask the human on the Codex side: MCP elicitation, and pausing the timeout clock

**What it is.**

- Codex forwards an MCP server's `elicitation/create` to its UI client as the
  server request `mcpServer/elicitation/request {serverName, threadId, turnId, …}`.
  The modes are form (`requestedSchema`), url (`url`, `elicitationId`) and a
  challenge form; the `openai/form` extension is declared in
  `InitializeCapabilities.extensions`.
- `thread/increment_elicitation` / `thread/decrement_elicitation` keep an
  "out-of-band elicitation counter" that pauses timeout accounting
  (`{count, paused}`).

**Evidence.**

- VERIFIED: the `McpServerElicitationRequestParams.json` variants and
  `ThreadIncrementElicitationResponse` ("Whether timeout accounting is paused").
- VERIFIED strings: `out-of-band elicitation` at 0.160.1 0xf08be30 and
  0.163.0 0xb386b3b.

**Min:** 0.160.1.

**Use.**

- A Magi server inside an interactive Codex could elicit a yes/no before a
  cross-machine DELEGATE with writes, instead of relying on the model to ask.
- A long blocking `wait:true` peer call could increment the counter so
  Codex's tool timeout does not fire while Magi waits on a peer.

INFERRED:

- that the increment is reachable from an MCP server and not only from an
  app-server client;
- how a TUI renders form elicitations.

Magi's headless worker refuses these requests by design (transport-recon.md),
which stays right.

### 10. Smaller reads Magi could take from the protocol

- **`thread/list` filters** (VERIFIED in the schema): `parentThreadId`,
  `ancestorThreadId` (subagent trees at any depth), `sourceKinds`,
  `searchTerm`, `useStateDbOnly` (no rollout scan), and `cwd` as a string or
  an array.
  - 0.163-alpha adds `excludedThreadIds`, and `readStates` in the response.
  - Use: deck subagent trees, from `ancestorThreadId` or the
    `state_5.thread_spawn_edges` table (locally 281 `open` edges).
- **`thread/readState/*` (new in 0.163)** gives unread results:
  `ThreadReadState{firstUnread: threadStart | turn{turnId}, revision}`,
  `thread/readState/update` and `thread/readState/changed`, stored in the new
  `state_5.thread_read_receipts` table. VERIFIED: 0.163.0 strings at
  0xb56ee4f and 0xb581159, absent in 0.160.1/0.162. The deck could mark
  "result not yet seen by the user".
- **`thread/items/read` (new in 0.163)** returns 1–100 items by id within a
  turn. VERIFIED: 0.163.0 0xb514fc3 and the 0.163-alpha schema. It can
  confirm a specific item after a notification.
- **`thread/turns/list` / `thread/items/list`** page history through the
  app-server, an alternative to opening `thread_history_1.sqlite` directly
  (VERIFIED, schema 0.160.1).
- **`InitializeCapabilities.optOutNotificationMethods`** lets a long-held
  connection drop per-token deltas server-side. VERIFIED, schema 0.160.1.

### Not worth Magi's time

- **Codex-native multi-agent.** `CollabAgentTool` is spawnAgent, sendInput,
  resumeAgent, wait, closeAgent, sendMessage, followupTask, interruptAgent and
  listAgents. `Op::InterAgentCommunication { id, author, recipient, trigger_turn }`
  is at 0.163.0 0xb3b030b. Both stay inside one Codex process's session tree.
  No app-server method submits an `InterAgentCommunication`. VERIFIED: absent
  from every `ClientRequest` list. parity.md's conclusion holds: keep the
  queue and steer.
- **Remote control** (`codex remote-control start|stop|pair`,
  `remoteControl/*`). The daemon enrolls with a ChatGPT-hosted relay for
  paired clients. VERIFIED by 0.163.0 symbols
  (`codex_app_server_transport::transport::remote_control::{enroll, client_tracker, server_api}`),
  headers `x-codex-server-id` and `x-codex-subscribe-cursor` (0xb5f65fa
  region), and `RemoteControlClient{deviceModel, platform…}`. It is
  account-bound and private; ssh plus proxy (1) does the same job on Magi's
  terms.
- **`environment/add` plus `codex exec-server`** keeps the model local and
  runs tools on another machine. See Same-harness notes. It is a different
  shape from Magi's peer model.

## Same-harness notes: Codex asking Codex on another machine

What Codex has natively:

1. **The desktop as a cross-machine orchestrator** (VERIFIED, asar).
   Desktop 26.1013 attaches SSH hosts through `ssh … codex app-server proxy`
   (Opportunity 1). Its `codex_app` tools (`list_threads`, `create_thread`,
   `send_message_to_thread`, `wait_threads`, each with `hostId`) let a desktop
   thread dispatch work to threads on other hosts and wait on them. Its
   coordinator prompt has the worker report back with
   `send_message_to_thread`. That is Codex-to-Codex across machines, but only
   inside one desktop's host registry, with tool approval set to `prompt`.
2. **A remote TUI on a shared app-server.** `codex --remote ws://host:port|unix://PATH`,
   with `--remote-auth-token-env`, attaches the TUI to another machine's
   app-server, and `codex agents --remote …` browses its sessions (VERIFIED,
   help). The server side is `codex app-server --listen ws://IP:PORT --ws-auth capability-token --ws-token-file …`
   or `signed-bearer-token` (VERIFIED, help).
3. **Remote execution environments.**
   - `codex exec-server --listen ws://IP:PORT|stdio` runs tools for a remote
     model loop; `--remote <URL> --remote-transport noise|direct` registers it
     with a backend; `forward --connect <URL>` relays.
   - On the app-server: `environment/add {environmentId, execServerUrl, authBearerToken?, connectTimeoutMs?}`,
     with per-thread or per-turn `environments:[{environmentId, cwd, runtimeWorkspaceRoots}]`
     and `thread/environment/connected|disconnected`.
   - `CODEX_EXEC_SERVER_URL` selects an executor, and forces embedded mode.
   - VERIFIED: help and schema. One local model then works on the remote
     filesystem. It shares no context or session with a Codex on that
     machine, so it is "a hand there", not a peer.
4. **Remote control** through the ChatGPT relay (see above). It needs an
   account and pairing.

What a Magi Codex-to-Codex route would need:

- **Addressing.** A remote Codex thread on a machine's daemon is reached
  through Opportunity 1 by `(host, threadId)`. Desktop-owned threads on a
  remote are reachable only through that remote's own desktop pipe (Magi's
  relay running there, as phase 2 already does with `deliverTo`).
- **The same-harness guard.** The set-aside Claude-to-Claude patch's rule
  (refuse local same-harness targets in favour of the native route) maps here
  to: refuse a local Codex-to-Codex card unless the target is remote. Locally
  Codex has its own multi-agent tools and the desktop's
  `send_message_to_thread`.
  - New in 26.1013, VERIFIED: the desktop refuses `send_message_to_thread`
    to a native ancestor ("cannot send to your native ancestor"). A Magi
    route should not deliver a child's report into its own parent by steer
    either. That is Codex's own call that collab `send_message` is the
    channel there.
- **Verified origin on the far side.** The remote Magi already verifies its
  own callers (`_meta.threadId` / `x-codex-turn-metadata`). Opportunity 7's
  attachment (`magi.card`) on both threads would let either side find the
  paired thread without trusting text.
- **Receipts.** On the daemon route, `item/completed` with
  `userMessage.clientId` equal to Magi's `clientUserMessageId` is the exact
  receipt, pushed (INFERRED from the schema; check live). `turn/completed`
  and `thread/status/changed` give finished and blocked.
- **Reply path.** Unchanged from phase 2: the remote peer answers through its
  own Magi MCP tool, and the relay streams the outbox home. A hook with an
  `mcpTool` handler on `Stop` (Opportunity 3) could prompt or verify that a
  reply was filed.

## Limits

- No decompilation (Ghidra not configured). Native evidence is literal
  strings and offsets; the Mac binary also has Rust symbols. Byte search
  finds literals, not behaviour. Rust packs strings without separators, so
  method names were matched exactly against the binaries' own generated
  schemas, not split from the packed runs.
- 0.163.0 (Mac) was not executed beyond `--help` and `daemon version`; its
  protocol schema was not generated, to leave the Mac unmodified.
  0.163.0-alpha.10.2 (desktop-bundled, Windows) stands in for schema-level
  claims. Its method list matches the 0.163.0 strings exactly where
  compared: `thread/items/read`, `thread/readState/update`,
  `thread/readState/changed`, and all 266 0.162 method names present in
  0.163.0.
- Live probes: only read-only `thread/list` / `thread/loaded/list` on
  Windows, with nothing loaded. Nothing was delivered, steered, injected,
  hooked or proxied.
- The daemon-proxy route is not tested end to end. The Mac had no daemon and
  no threads; the local socket refused. That the proxy carries raw bytes
  (so WebSocket framing runs over ssh) rests on its help text and the
  desktop's code, not on a run.
- The desktop was not running, so the `codex_app` pipe's `tools/list` and
  `wait_threads` results were not observed. Tool definitions come from asar
  code.
- The Mac's `thread_history_1.sqlite` absence is one observation of a fresh
  install.
- Scratch artifacts:
  - `scratchpad/rea/` holds the schemas, method lists and `deps-*.txt`
    string tables;
  - `scratchpad/scripts/` holds `scan.mjs`, `methods.mjs`, `defs.mjs`,
    `defdiff.mjs`, `blob.mjs`, `probe-list.mjs`, `peek.mjs` and
    `schema.mjs`;
  - the 250 MB Mac binary copy is `scratchpad/rea/mac163/codex`.
