# Oh My Pi 18.14.0: what changed for Magi (2026-10-29)

Static reading of the published npm package `@oh-my-pi/pi-coding-agent@18.14.0`
(14,860,953 bytes, downloaded from registry.npmjs.org, unpacked into a scratch
directory, `src/` and CHANGELOG read). **Nothing was run from it.** The
installed omp is 18.10.4 and `VERIFIED_VERSIONS.omp` is 18.4.4; neither moved.
The `dist/` bundle was not read, only `src/`.

Two background agents read the source in parallel; the two findings that
needed Magi edits, and their enum and default, were then checked by me in the
package source and in Magi's code. Everything else below is the agents' report
and was **not** re-checked by me.

## Changes that needed a Magi edit

| Finding | 18.14.0 source | Magi edit |
|---|---|---|
| A fourth approval mode, `always-ask-cached`: `--approval-mode` accepts `always-ask`, `always-ask-cached`, `write`, `yolo`. It prompts for every call until the user remembers a grant. | `src/cli/flag-tables.ts:258-262`, `src/commands/launch-help.ts:134-135`, `src/extensibility/extensions/wrapper.ts:262` | `approvalToClass`, `ompConfiguredApprovalMode` (`src/omp-launch.mjs`) and the extension's `APPROVAL_MODES` (`omp/magi-omp-extension.js`) accept it as `prompting`. Before, a session on it read as an unknown mode and the Claude envelope asserted nothing. Magi's own launches never use it, so `src/serve.mjs` is unchanged. |
| `advisor.continueSeverity` (enum `nit`, `concern`, `blocker`), default `concern`, with `protocolDefault: ["rpc","acp"]`: an advisor note at or above it that arrives after the final answer wakes the worker. | `src/advisor/settings.ts:65-88`, `src/session/session-advisors.ts:1729-1840` | `writeAdvisorOverlay` (`src/omp-advisor.mjs`) writes `advisor.continueSeverity: blocker`, advisor on or off, restoring the pre-18.14 behaviour for a one-request run. |

The overlay key is safe on older omp: 18.10.4 reports `Unknown setting:
advisor.continueSeverity` from `omp config get`, but `omp --mode rpc --no-ui
--no-extensions --no-skills --config <overlay>` with and without the key
started, answered, and emitted the same `config_warnings_changed` event. The
warning's text was not read.

Not seen: whether a woken worker races Magi closing stdin after the final
answer. That reasoning is inferred from the source; the pin to `blocker`
removes the case rather than proving the race.

## Reported by the agents, not re-checked by me

- **No new cross-process messaging.** The IRC bus is still process-global;
  collab is still the only cross-process route. Subagent approvals still reach
  no one, so plan review stays TUI-only.
- **Unchanged:** every launch flag Magi passes; the rpc handshake and frames
  Magi uses; extension events and discovery; session-file and advisor-note
  reads; `--config` overlay merging and keys.
- **Stricter `--model`:** a provider-qualified selector must name an exact id.
- **`tools.restrictedFolders`** still prompts under `yolo`.
- **Continuation id/file:** a session can change its id and file when another
  omp process holds the file.

## Open: does a note into an approval prompt deny it?

In the TUI, any visible queued message cancels a pending approval dialog and
counts as a deny (agent report). It does not apply to rpc. Magi's extension
already sends a steer to an omp session that is waiting on an approval as an
`aside` (`test/shim-agent.test.mjs`, "an omp session waiting on a tool approval
reads as blocked"); whether an `aside` also avoids the deny was not tested on
a live session.
